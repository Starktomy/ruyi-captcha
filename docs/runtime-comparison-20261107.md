# 2026-11-07：新上游底座与旧完整 fork 的资源对比

本页保留恢复性能优化前 `b9877c4` 的历史测量。优化已合回内核 main，最新同底座
结果见[性能恢复报告](runtime-restoration-20261107.md)。

当前 **上游 0.3.5＋少量兼容补丁** 在本轮 CapSkip `site_url + sitekey` 路径上，
CPU 和内存成本都高于之前的完整 fork。内核补丁更少，并没有在这个工作负载上更省资源。

## 结果

以下各单元格为 **旧完整 fork → 当前精简内核**。CPU 是每个成功取得的 token
消耗的整个进程树 CPU 秒；PSS 是同一批所有进程的峰值之和，再取三批中位数。
2/4 并发的 PSS 是整批内存，不能当作单任务内存。

| 并发 | CPU 秒 / token | CPU 变化 | 峰值 PSS，MiB | PSS 变化 | Token 延迟中位数 |
| --- | --- | --- | --- | --- | --- |
| 1 | 4.312 → 4.990 | +15.7% | 354.7 → 460.9 | +29.9% | 3.365 → 4.406 秒 |
| 2 | 4.168 → 4.882 | +17.1% | 618.0 → 838.2 | +35.6% | 3.438 → 4.449 秒 |
| 4 | 4.364 → 5.300 | +21.5% | 1095.5 → 1467.5 | +34.0% | 4.595 → 5.752 秒 |

对应三档峰值 RSS 为旧版 476 / 889 / 1722 MiB，当前版 692 / 1348 / 2595 MiB。
RSS 会重复计算共享映射，容量评估优先看 PSS。

两个主要版本各取得 token 21/21；另有“旧原生内核＋新 helper”对照也是 21/21。
各版本还做了一次不计入表格的预热，共 66 次调用全部返回非 dummy token。
所有测量批次清理后均无残留进程。这些资源批次不包含站点后台提交；后台接受由
此前 SDK/API 和内置 wheel 的独立 live 验收确认，并非本轮每一个 token 都进行了后台验证。

## 排除 helper 的影响

保留旧原生二进制，改用当前版本的 Necko helper，再与当前内核比较：

| 并发 | 旧内核＋新 helper：CPU 秒 / token | 当前：CPU 秒 / token | 旧内核＋新 helper：峰值 PSS | 当前：峰值 PSS |
| --- | --- | --- | --- | --- |
| 1 | 4.229 | 4.990 | 342.0 MiB | 460.9 MiB |
| 2 | 4.098 | 4.882 | 603.4 MiB | 838.2 MiB |
| 4 | 4.133 | 5.300 | 1102.1 MiB | 1467.5 MiB |

使用相同 helper 后，旧原生内核仍然更省。这支持主要差距来自原生内核及其构建内容，
包括旧 fork 保留、当前精简时移除的性能实现。本轮没有逐项恢复补丁，不能把差值
精确归因到某一项缓存，也不能据此声称上游某个优化造成了回退。

## 方法与边界

- 当前内核：`b9877c412c779bb783da1db523806b14732a881d`，上游底座 `0ab7201` / 0.3.5。
- 旧完整 fork：`158eae70e9cc78b263474aca58bc42d10412c990`，保留的原生二进制和旧 helper。
- 两边使用同一份当前 Python Context 绑定、ruyi-captcha provider、Linux Firefox 159 profile、
  真实 CapSkip sitekey、system clock、直连；每次尝试新建 Context，timeout=30、attempts=1。
- 预先完成 Python 导入与内核能力探针，再把调用进程移入独立 cgroup 后开始计时。
  统计 Context 启动、JS/Worker、helper/DNS 子进程和清理的 CPU，排除外部采样器。
- CPU 读取 cgroup `cpu.stat` 差值，避免只统计直接子进程而漏掉孙进程。
- 主机为 AMD EPYC 7643，可用 5 个逻辑 CPU、约 9.66 GiB 内存。
  外部采样器的 CPU 与批次时间之比中位数约 0.33 核；其 CPU 未计入结果，延迟仍可能受到采样竞争影响。
- 同时对整个存活进程树每 50 ms 采样 PSS/RSS；包含 Python 调用方。采样可能漏掉短暂峰值。
- 1/2/4 并发各三批，三个版本轮换、交替顺序，批次依次运行。
  本表采用完整正式复测，期间没有同时执行本机编译或测试套件；探索轮另存。
- 这是一台 Linux 主机上的小样本，包含网络和挑战变动，不能推导长期成功率或固定延迟。
  本次是 `site_url + sitekey` 组件路径；完整 CapSkip 页面约 110 秒的结果属于另一工作负载。

逐批数据、机器信息、二进制和 helper 散列见
[runtime-comparison-20261107.json](runtime-comparison-20261107.json)。

## 对维护方向的建议

继续使用新上游作为底座，但“保持内核精简”应当控制业务耦合，不能只按补丁数量衡量。
旧 fork 的通用字体、样式和布局优化仍有保留价值。应按采样热点分组恢复，保留上游已有
优化，每组同时验证浏览器行为和真实资源收益；验证码厂商状态机继续放在本仓库。
这样才能兼顾跟进上游和运行成本。

复现工具是 `tools/benchmark_runtime.py`，需要 Linux cgroup v2 的子组创建权限，以及
已保留的旧二进制/helper。结果不会保存响应 token。
